# 02. 三个业务里程碑、七个实施工作包与发布门禁

## 执行模型

2026-09-13 修订：企业逻辑改为独立扩展包/应用外壳，核心仅补必要通用扩展点并收敛旁路；默认继续使用 LightRAG Server。保留 **M1 单租户 Kubernetes → M2 多租户及租户管理界面 → M3 统一运营后台** 三个业务里程碑，研发按 **A1/A2/A3、B1/B2、C1/C2 七个工作包** 推进。工作包是集成验收单元，不是七套系统，也不要求七次生产上线。

[OpenSpec tasks](../../openspec/changes/replace-rollout-with-three-production-stages/tasks.md) 是唯一任务勾选记录。本文规定范围、依赖及发布门禁，领域文档解释具体设计。本次只调整方案，所有业务实施任务仍未执行。

- 生产组件直接替换为最终实现，不建设 SQLite/PVC、文件型多租户、双写或临时认证系统。
- 配置/现有注入/插件优先，企业实现置于 `deeptutor_enterprise` 包；[13](13-deployment-and-upstream-sync.md) 的核心 seam/真实调用清单与 [06](06-postgresql-native-store-plan.md) 的 LightRAG 服务契约纳入相应工作包，不新增独立重写阶段。
- 默认复用原版固定 workspace LightRAG Server，经企业授权路由服务使用受控实例池；不按租户复制整套 DeepTutor，不以一个共享 Server 的不同 KB 名称做隔离。
- 一个任务覆盖适用的 **数据约束/迁移 → 服务逻辑 → 真实入口 → 权限/异常 → 测试 → 切换说明**，不是仅创建表或编写接口类。
- A1/A2 在集成环境分批验证，A3 汇总验收后才发布 M1；未完整替换的存储状态不能作为正式生产版本。
- B1 先用一个真实 EduPlus2 租户验证最终接入，B2 再开放多个租户；C1/C2 分批完成运营功能，不把 C2 从最终交付范围删除。
- Woodpecker 流水线开发纳入 A3 必交付子环节，从 A1 并行建设；后续阶段复用，不新增业务工作包。
- 可用性、容量和多副本由独立工作线 H 管理，不由租户数量决定，不增加第八个业务工作包。

## 文档与任务的执行顺序

领域文档现按 [readme 索引](readme.md) 的 00–13 编号顺序组织：00–02 先确认目标/基线/主计划，03–07 对应 M1 的稳定契约、环境、流水线和存储资源，08–11 对应 M2 接入与隔离，12 按 B2→C1/C2 交付两级管理界面，13 为从首发即生效的持续发布/upstream 维护规则。编号不是新增阶段，也不将跨阶段安全/维护工作后移。

A3 包内任务同步按执行顺序重排：3.1–3.4 接入/环境/权限/CI 从 A1 并行，3.5–3.9 镜像/制品/网络/迁移/部署随 A1/A2 增量接入，3.10–3.14 汇总首发完整功能与故障/恢复/smoke，3.15 放行，3.16 发布确认。任务组仍按 A1/A2/A3/B1/B2/C1/C2/H 归属排列；4.1 外部契约、8.1/8.2 运行目标和可靠性不等前面任务组全部完成才开始。

## 总览与依赖

| 里程碑 | 工作包 | 输入依赖 | 完成证据 | 是否代表正式发布 |
| --- | --- | --- | --- | --- |
| M1 | A1：结构化状态替换 | 首发功能与存储契约确认 | 固定 tenant/user 的 PG 真实读写、所有权、配置与审计闭环 | 否 |
| M1 | A2：文件与检索替换 | A1 的稳定 ID/metadata 契约；集成时需对应 PG 实现 | S3/对象配额/scratch/KB-RAG 全链路与故障补偿 | 否 |
| M1 | A3：单租户生产验收 | A1/A2 完成；部署准备从 A1 起并行 | Woodpecker 真实交付链路、G1、运行模式可靠性及版本/恢复记录 | 是，M1 |
| M2 | B1：EduPlus2 单租户闭环 | M1 作为接入验证基线；外部配置准备提前并行 | 首租户最终登录、身份绑定、权限/撤权与业务访问闭环 | 可受控发布单租户集成版本，但不标记 M2 完成 |
| M2 | B2：多租户与租户自管理 | B1 的契约/身份/权限闭环通过 | 两租户隔离、治理后端、现有租户管理 UI、G2 | 是，M2 |
| M3 | C1：运营管理闭环 | M2 治理 API、策略执行及租户界面 | 跨租户开停/分配/配额/角色/操作审计闭环，G3a | 可先发布运营基础版，不标记 M3 完成 |
| M3 | C2：运营治理完善 | C1 能力/权限契约与底层用量/任务状态 | 用量分析、任务治理、同步状态、审计查询/导出及 G3 | 是，M3 完整交付 |

```text
A1 存储契约 ──→ A1 业务闭环 ─┐
       └─────→ A2 文件/检索 ─┴→ A3 / G1 → M1
Woodpecker/镜像/部署准备（与 A1 并行） ──→ A3 / G1
外部配置准备（与 A1 并行） ───────────────→ B1 → B2 / G2 → M2
                                                        → C1 / G3a → C2 / G3 → M3
部署/监控/恢复、安全回归、upstream 同步、H 可用性工作线贯穿全程
```

依赖是验收依赖，不要求团队完全串行。基础设施清单、EduPlus2 注册/测试账号、接口契约校验可以提前做；缺少前置验收时不能开放对应生产能力。K8s 测试环境提前部署只用于集成验证，不是允许原生 SQLite 过渡生产上线。

## M1：单租户 Kubernetes 正式上线

### A1：结构化状态替换

先确认首发功能清单、实际存量和用户归属、目标容量及可用性要求，再固定内部 tenant/user ID、Store/metadata 契约。同步核查配置/插件/容器注入可复用点，登记必须补齐的通用核心 seam 和企业包责任；明确 KB/workspace 数量、Server 实例池预算、锁定 LightRAG 版本和图后端验收条件。已有必须上线的能力不得静默删除；可选能力未启用的决定需要记入发布范围，不无限扩展为支持所有上游可选插件。

按可观察行为拆分：

- 本地登录/账号、单租户多用户所有权与受控管理员初始化。
- 创建/继续会话、消息/turn/event 事务持久化；历史、事件重放、regenerate/reply/cancel 等调用路径。
- 设置保存到运行时读取、模型目录/Secret 引用、资源 grants。
- memory、notebook、KB metadata、可编辑资源 metadata、审计等各自真实读写链路。

DeepTutor 应用租户表从第一天具备 `tenant_id`、复合约束和 RLS；平台数据显式分开。独立 LightRAG 索引使用 [06](06-postgresql-native-store-plan.md) 的 workspace/受限凭证/数据库隔离契约，不假设原版自动具备 tenant 列或 RLS。直接 SQLite/JSON 调用不能留在生产旁路。内部 ID 后续只绑定外部身份，不重写资源所有权。

**A1 验收**：每项 PG 行为有真实入口、并发/错误/所有权测试及旧生产写路径退出证据。还未接通 S3/RAG 时只能认定 A1 工作包完成，不能认定单租户产品可发布。

### A2：文件与检索替换

A1 契约确定后可并行开发，按附件、生成物、知识库等完整行为接入：

1. S3-compatible 流式读写、私有对象授权、短 TTL URL 和失败重试，在目标服务验证。
2. 对象额度 PG 预留/核算/释放、pending/ready 状态及孤立对象清理，在 M1 完成；不是等待 B2 的 token/并发治理。
3. 附件上传/metadata/预览/下载/删除与所有权闭环。
4. scratch 下载→文件工具处理→S3 上传→PG 提交→成功事件；Pod 中断不得虚报产物成功。
5. KB 原文、解析物、索引、召回、源文引用、删除及重建全链路，含需要的 KV/图状态。
6. 可编辑 skills/personas 及首发必需高级能力的正文、配置、执行读取统一接入最终存储。

默认保留当前 `lightrag-server` 查询协议与 LightRAG 检索引擎，企业包实现 PG/Secret binding、可信调用凭证、查询前授权、固定 workspace Server 路由和文档管理。A2 包含实例开通/重启/回收、全部索引 PG 状态、S3 原文/解析物、引用映射、删除/重试/重建及独立数据库防线；不能仅把客户端接通或安装 pgvector 当成完成。

稳定 namespace 使用内部 tenant/KB/index-version，不使用绝对 scratch 路径。已有本地 `lightrag` 文件索引仅按真实存量评估只读导入或重建；非托管外部连接默认只解除绑定，转企业托管须核实语料归属和移交，不静默删除用户远端数据。具体契约以 [06](06-postgresql-native-store-plan.md) 为准。

**A2 验收**：目标存储契约与每个调用链同时通过；无任意对象 key、越权下载、超额上传、孤立 metadata 或仅在原 Pod 能读的产物。

### A3：单租户生产验收

**部署工作从 A1 起并行启动，A3 是最终集成验收，不是第一次接触 Kubernetes。** 提前开发 Woodpecker 流水线，准备生产镜像/清单、测试 namespace、PG/S3、Secret、Service/Ingress/TLS/WS 和 probes，将 A1/A2 的增量功能持续放到同构环境验证。

流水线按“接入契约 → 质量检查与生产镜像适配 → 不可变制品 → 测试环境迁移/部署/smoke → 受控生产晋级与回退”细化，分别有真实验证；完整方案见 [05](05-woodpecker-kubernetes-pipeline.md)。源仓库已有 GitHub Actions，但当前没有 Woodpecker 配置；现 Docker 入口的本地 JSON 配置与前后端合并启动需适配，不能只新增部署 YAML。

A3 汇总首发功能回归、所选运行模式验证、故障/备份恢复、存量切换及发布证据。示例配置是拟新增契约，不代表当前 repo 已实现：

```bash
DEEPTUTOR_DEPLOYMENT_MODE=single_tenant
DEEPTUTOR_DEFAULT_TENANT_ID=<稳定内部 UUID>
DEEPTUTOR_STORAGE_BACKEND=postgres
DEEPTUTOR_OBJECT_STORE=s3
DEEPTUTOR_RAG_PROVIDER=lightrag-server
DEEPTUTOR_RAG_GATEWAY_URL=<internal-service-url>
AUTH_ENABLED=true
```

M1 不等待 EduPlus2 接入或新运营界面；现有单租户管理功能继续可用，平台 Secret 不可被页面/API 导出。

### G1：M1 发布门禁

G1 区分**发布前放行**和**发布后完成确认**：先在同构测试环境完成 A1/A2、故障/恢复/安全及适用 G-H，检查生产配置并取得批准；再受控部署生产、执行隔离 smoke 并归档证据，最后确认 M1 上线。不能要求“先有生产成功记录才允许首次部署”，也不能因已经部署就跳过后验或提前开放普通业务流量。

| 验证 | 通过标准 |
| --- | --- |
| Woodpecker 自动交付 | 目标 agent 实跑检查/构建/推送/迁移/部署/HTTP+WS 业务 smoke，同 digest 经批准晋级生产；证据可追溯 |
| 流水线安全与故障 | 非可信来源/未批准/环境错误拒绝；迁移失败阻断，发布互斥/旧构建/中断恢复/兼容回退演练通过，无 Secret 泄露 |
| 首发功能清单 | 登录、聊天、历史、KB/RAG、附件、memory/notebook、产物、管理设置和已启用能力均完成真实替换 |
| 重建 Pod/清空 scratch | 账号、配置、历史、KB、文件可恢复；不依赖原 Pod 本地状态 |
| PG/S3/必要 RAG 服务失败 | 就绪检查或相应操作明确失败；不写 SQLite/local fallback，不切换默认检索 workspace，不返回未持久化/未索引成功 |
| 企业扩展与调用覆盖 | 企业启动器实际安装身份/Store/RAG providers；缺 seam/版本不符拒绝启动，所有已启用 API/tool/worker 无旧写旁路 |
| LightRAG 完整链路 | 固定版本/图后端及低权启动、绑定/workspace 核对、导入→召回→授权源文→删除/重建；清空 Server scratch 仍可恢复 |
| 并发/重复请求 | 事件顺序、唯一约束、对象预留/核算与幂等正确 |
| 对象故障与安全 | pending/孤立对象/删除重试可修复；任意 key、超额、过期 URL、他人资源拒绝 |
| 认证及 Secret | 未认证 401，越权 403/404，管理员也不能导出平台明文凭证 |
| 运行模式 | 单执行模式通过排空/在途失败/重连/容量验证；要求高可用或启用多执行者则必须先通过 G-H |
| 成套恢复与切换 | PG/S3 引用一致；记录实测 RPO/RTO，旧写入关闭，回退兼容范围明确 |

## M2：多租户及各租户管理界面

### B1：EduPlus2 单租户闭环

**外部准备提前，生产开放分步。** 在 A1/A2 期间就协调 EduPlus2 app 注册、测试租户/账号、redirect、Handoff/OIDC、权限和 Webhook 契约；不要求 M1 完成登录集成，也不把准备活动做成独立过渡项目。

以 M1 的一个固定内部租户为验证对象，交付最终实现：

- 签名/claims/code/state 校验、身份映射、`/me/profile`、具体操作权限与会话生命周期。
- 显式绑定原内部 tenant/user 到外部 tid/eui，幂等可回退；不按同名合并账号，不搬 PG/S3。
- HTTP/WS/后台任务可信上下文、权限依赖失败拒绝、用户/租户停用及撤权传播。
- 首租户所需事件接收与权限缓存失效路径，签名校验且 PG 持久化接收后才确认；不能把安全依赖留到 B2。
- 用首租户真实账号完成“工作台进入→聊天→KB/附件访问→重新登录/撤权”验证。

**B1 验收边界**：其他未绑定租户仍被拒绝；学校管理员不映射全局 admin。使用最终 adapter，不另建临时 token 透传或认证网关。可受控发布单租户接入版本，但它不代表完成 M2，也不要求已完成全部租户管理 UI。

### B2：多租户与租户自管理

B1 接入闭环通过后，使用同一底座逐项交付：

- 租户初始化/失败重试，暂停和恢复各有幂等状态机、权限与审计。
- 平台给租户分配模型/功能范围；租户 grants 不越过平台或外部权限上限。
- 用量记录、token 额度与并发预留/释放分项验收；额度在真实 agent/tool 与受管索引任务生效，远端检索/embedding/导入用量单独记录，不默认包含在聊天 cost_summary。
- PG/RLS/连接池、owner/grant、S3、向量/图检索、cache/job、SDK/M2M 全链路租户隔离。
- 必要组织关系缓存、周期对账、多租户 Webhook 幂等/重试/撤权；不重建全部 EduPlus2 主数据平台。
- 在现有管理界面微调租户标识、KB、用户授权、设置/模型选择及菜单/路由/按钮权限；不复制每租户前端或 Deployment。

B2 开放跨租户治理 API 前先完成可信平台身份/具体能力/目标租户绑定及默认运维授权，相关默认数据走版本化迁移并验证无权限拒绝；C1 复用并完善运营角色和界面，不是首次补鉴权。租户开停、授权和配额先提供受保护、可审计的管理 API/运维入口；租户管理员使用本租户界面。**治理与安全后端不等待 C1，统一运营界面不反向阻塞 M2。**

### G2：M2 发布门禁

- B1 首租户接入通过；集成环境新增第二租户及各自管理员/普通用户，全量正负向验证后才开放多租户生产流量。
- 相同外部 eui、KB 名称、猜测 session/object ID、伪造 scope 均不串租；已有首租户数据和对象 key 不变。
- 所有入口、数据库连接池、检索、缓存、对象下载与后台任务均验证租户/用户边界；LightRAG 相同 KB 名称、错误 binding/调用凭证/workspace、跨语料图污染与数据库跨 workspace 读写均有拒绝负例，不能先跨租户检索再过滤。
- tenant_admin 默认管理本租户；自定义权限角色正例及无权限 403/隐藏菜单负例通过，无平台 Secret/跨租户管理入口。
- 开停/撤权影响旧 token、WS、新 turn、下载授权与任务派发；短时 URL 的撤权时效明确。
- 模型策略、token/并发额度和失败释放真实生效，统计/审计可解释，不只是 UI 显示限制。
- **不要求因“第二个租户”就启用第二个 Pod。** 可接受单执行模式时记录容量与维护窗口；多副本或 HA 为发布目标时，G-H 成为本次 G2 的前置，不允许绕过。

## M3：统一运营管理后台

### C1：运营管理闭环

前置是 M2 已交付。复用 B2 服务，实现：平台角色与 `/ops` 入口、全租户目录/详情、开通/暂停/恢复、模型/功能/配额分配、平台模型与 Secret 引用/轮换、受控角色授权、操作结果及基本审计可查。

**G3a 工作包门禁**：每个写操作前后端同权限、状态和幂等一致，实际影响运行时；operator/auditor 无越权能力，tenant_admin 不能进入运营 API，租户管理界面继续可用。C1 可单独发布为运营基础能力，但不能声称 M3 全部完成。

### C2：运营治理完善

复用已有用量/任务记录，逐项完善：按租户/时间的用量及费用估算、存储/错误概览、同步/Webhook/导入/turn 状态、授权重试/取消、审计高级筛选与导出。费用估算不冒充计费结算，任务重试不承诺外部副作用 exactly-once。

C2 的查询开发可在 C1 契约稳定后并行，最终验收依赖 C1 角色和入口；不能在没有权限约束的临时后台演示。**C2 保留在本次完整范围，不因 C1 可发布而省略。** 两级管理边界见 [12](12-platform-operations-admin.md)。

### G3：M3 完整发布门禁

- C1/G3a 与 C2 全部完成；覆盖完整 [12 权限矩阵](12-platform-operations-admin.md)。
- admin/operator/auditor、tenant_admin、普通用户及自定义授权角色的入口/API 正负向一致。
- 开停/策略/配额、并发修改、重复提交、任务重试/取消和审计结果符合实际执行状态。
- 聚合统计不默认读取私有对话/附件；导出单独授权，Secret 不回传明文，无任意 tenant override 或超级连接旁路。
- 用量口径、失败处理、日志/审计脱敏及此前 M1/M2 功能回归通过；本次运行模式要求的 G-H 证据仍有效。

## 独立工作线 H：可用性、容量与多副本

H 不与 M2 绑定。A1 开始记录目标并选择运行模式，每次正式发布重新评估；本方案不凭空指定 SLA 或压测阈值，实际目标必须进入发布记录并取得业务/运维确认。

| 运行模式 | 适用条件 | 必须满足 |
| --- | --- | --- |
| 单执行模式 | 容量足够，明确接受非 HA、维护窗口与故障中断 | 限制并发执行者，排空/恢复/超时清理/配额仍正确；业务与运维确认并留证据 |
| 多执行者/高可用模式 | 首发或任意后续发布的容量/可用性要求触发，或实际启用多 Pod/多 worker 竞争执行 | 先实现协调并通过 G-H；不能仅改 replicas、加 sticky session 或依赖 PG/S3 自动恢复 |

**G-H 在启用多执行者前强制通过**：

1. durable turn/job/command、原子领取、owner lease/fencing，旧执行者失效后不能继续提交。
2. 请求落任意 Pod 的订阅、事件游标重放、cancel/reply、重复命令幂等和权限一致。
3. 执行者故障、网络中断、滚动更新与扩缩容下状态可解释，不遗留无限 running 或重复核算。
4. 对象额度、token/并发预留及释放在适用发布功能范围内一致，故障重试不重复产生已完成副作用。
5. 检查 PG/S3、Ingress/连接路由、队列（如有）等依赖故障与恢复目标；两个 backend Pod 本身不等于端到端 HA。
6. 压测及故障演练满足本次已确认目标，记录允许中断/恢复语义，不承诺未实现的 agent 自动续跑。

单执行模式只验证当期能力并记录 G-H 未触发及扩容前置任务；**不把未做的多副本任务勾为完成**。H 目标评估、基本监控/恢复、安全与 upstream 回归无论何种模式都不能跳过。

## 任务粒度与完成标准

七个工作包在 OpenSpec 中各有一个任务组，H 单列条件性任务组，不是第八次上线。原大项拆成可审查的行为，例如“租户暂停”和“租户恢复”“并发预留”和“用量核算”“附件下载授权”和“对象补偿”，避免一个 checkbox 包含数个独立子系统。

每项任务完成需满足：

1. 适用数据迁移/约束和旧数据处理已交付，未涉及说明理由。
2. 接入真实 UI/API/agent/worker 调用；基础设施任务用实际命令/部署路径验收。
3. 权限、校验、并发、幂等、失败恢复等适用要求有实现和负向证据。
4. 存储替换后原生产写路径退出，不能用 stub/mock 演示代替目标依赖集成测试。
5. 有清晰依赖、验收记录及切换/回退说明；未完成部分不能靠在文档中描述来勾选。

任务以可独立审查的 PR/变更为单位；文件数量少不是目标。存在多个独立用户行为或无法解释完成证据时继续拆分；不要按“先所有 SQL、再所有后端、最后所有 UI”的水平层切割。

## 数据切换：一次迁入，不建设双写

### 无存量数据

第一阶段直接初始化 PG/S3；不要为不存在的旧数据开发通用迁移平台。第二阶段只扩展租户映射及必要字段，第三阶段不换存储。

### 确有存量需要保留

1. 明确资源所有者与目标内部 tenant/user，旧全局 admin 数据不自动公开给租户。
2. 一次性导入工具提供 dry-run、源只读、备份、资源数量/校验和/引用完整性验证、幂等断点与迁移审计。
3. 在维护窗口停止旧写入，导入 PG/S3 并验证；启用目标系统写入后旧库只读归档，不回写同步。
4. 导入前失败可继续原系统；目标系统产生新写入后，不允许简单切回旧 SQLite 丢弃新数据。使用兼容当前 schema 的应用回滚，或停止写入后按批准的 PG/S3 备份恢复流程处理并明确数据损失窗口。

迁移 SQL/默认角色/历史映射走版本化迁移，不在每个 Pod 启动时无版本修补数据。EduPlus2 的 OpenFGA/Keycloak 变更由其受控 provider migration 执行；本仓库不直接改外部运行态。本次只更新文档，未新增或执行实际迁移。

## 发布与官方更新

M1 建成的 Woodpecker 流水线在 B1/B2/C1/C2 和官方更新中复用：构建一次、按 digest 晋级，测试与生产凭证隔离；迁移、部署、业务 smoke 和回退共用环境锁，不通过手工直改集群绕过门禁。每次发布必须验证同版本/拓扑适用的门禁证据，缺失或失败不得放行。

每里程碑发布记录流水线 ID/批准人/目标环境/制品清单与工作包状态、运行模式/容量及可用性目标、upstream SHA、自有 SHA、镜像 digest、schema/对象格式、启用能力、验证证据、已知限制和回滚兼容范围。后续合并官方更新必须重跑当时已发布的 G1/G2/G3 及适用的 G-H，不把官方 SQLite/file 新路径重新带回生产。

## 文档读者核对问题

1. 是否从三个阶段变成七套系统/七次生产上线？不是，三个业务里程碑下有七个集成验收工作包。
2. 是否等 A1/A2 完成才准备 K8s？不是，部署和外部契约准备从 A1 并行，A3 才是完整生产验收。
3. B1 是临时认证方案吗？不是，在一个真实租户验证最终实现，B2 扩大租户集合。
4. 租户界面与运营界面何时交付？B2 交付租户界面；C1/C2 交付统一运营能力并保留租户界面。
5. 多租户是否强制两个 Pod？不因租户数量强制；运行目标决定是否触发 G-H，多执行者未验收不得开启。
6. C1 可发布是否表示省略 C2？不是，M3 必须完成 C1+C2。
7. 无时间做过渡是否可以跳过验收或静默删功能？不可以；只调整研发粒度，不减小已确认完整范围。
8. Woodpecker 是否另增一个阶段？不是，A3 内细化开发子环节，从 A1 并行，G1 前必须真实交付，后续复用。
9. 是否已经实施？没有，本次更新企业包/外壳和 LightRAG Server 方案，未修改业务代码、创建或触发实际流水线。
10. 是全产品零改源码吗？不是；优先配置/现有扩展点，必要通用核心改动与真实调用收敛仍需完成，不用厚壳或运行时 monkey patch 伪装低维护。
11. 保留 Server 是否不用做 A2？不是；现成连接只负责查询，托管文档、PG 全索引状态、S3 源文、引用、删除、权限与恢复仍需企业服务补齐。
