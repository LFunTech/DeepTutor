# K12 容量评估与验收基线 v1

日期：2026-09-14。用户已委托由实施方评估学生、教师、家长及作业、答疑、知识学习、生涯规划、心理支持等场景的容量。用户随后明确“按照这个评估继续”，本基线作为实施/验收目标。本文补全本 change task 1.47，不另立平行实施计划。

**结论：首期按 3,000 学生、约 8,000 账号、600 人同时在线、一学年存量验收；按 30,000 学生规划下一扩容档。** 下述数字是明确假设下的工程目标，不是行业统计、真实用户预测、已经测得的系统能力或采购承诺。评估完成不等于容量验收通过；task 1.47 暂不勾选。用户不必再替我们填写容量阈值。

## 1. 规模与使用强度

学校有不同学段/规模，不能用一个全国校均值代替产品负载。这里把“单校”作为容量单元，不要求每个真实租户恰为一所学校，也不按租户复制整套服务。

| 档位 | 学生 | 教师/教学管理账号 | 家长账号 | 账号合计 | 常态日活账号约数 | 高峰在线目标 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| P0：试点 | 300 | 30 | 450 | 780 | 200 | 60 |
| P1：首期容量单元 | 3,000 | 300 | 4,500 | 7,800 | 2,000 | 600 |
| P2：多校扩容规划 | 30,000 | 3,000 | 45,000 | 78,000 | 20,000 | 6,000 |

假设与计算：
- 每学生预留 1.5 个家长账号、每 10 学生预留 1 个教师/管理账号，均是容量预留，不是实际师生比或强制建号规则；兄弟姐妹与多角色账号应按真实主体去重。
- 学生/教师/家长是容量场景分组，不等于本次新增三套认证 role；压测账号使用当前批准的身份/preset/grant 契约。容量覆盖某场景不表示该场景全部产品功能已由本次数据库迁移交付。
- 常态学生日活 50%、教师 30%、家长 10%，因此 P1 为 `3000×50% + 300×30% + 4500×10% = 2040`；高峰在线取约 30% 日活的向上整值。
- 按每年 200 个活跃学习日、每活跃学生每天 8 轮 AI 交互、每轮至少一问一答估算。教师与家长的额外 AI 交互总量预留学生的 25%。一轮业务 turn 可以有多个模型请求，不能与供应商请求数等同。
- P1 常态年度业务 turn：`3000×50%×200×8×1.25 = 300 万`；消息至少 `600 万`。学生日活提高到 100% 时为 `600 万 turn / 1200 万消息`。假期/周末使用增加时，应替换 200 天假设，不能当作零负载。
- 连续辅导、心理支持等更可能拉长上下文与会话；教师批改/备课更可能增加批量任务、工具调用与输出长度。不能给每个新增场景机械复制一套全部日活数据；用同一主体的总交互量、场景混合与长尾分别建模。

## 2. 单用户存量与 P1 数据集

年度指标是活跃学生的使用模型，不是限制用户只能保存这么多数据。重度尾部用合成数据验证，不要求收集真实未成年人原文。

| 数据类别 | 活跃学生年度常态 | 重度单用户验证值（累计） |
| --- | ---: | ---: |
| 聊天消息 | 3,200 条（1,600 轮） | 100,000 条，含分支、取消、继续/重新生成 |
| 会话 | 约 160 个，平均 10 轮/会话 | 10,000 个；另有单会话 3,000 条消息 |
| 收藏题目/错题条目 | 800 条 | 20,000 条、200 分类、真实多分类关系 |
| 答题/学习交互 | 4,000 条 | 100,000 条及对应顺序事件/CAS 历史 |
| 阅读材料引用 | 200 个 | 5,000 个，含重开、排序、删除与跨域引用 |
| 阅读标注/笔记/进度 | 2,000 条 | 50,000 条；不把每次滚动必然计为永久记录 |

P1 基准数据集（所有已有领域仍须功能覆盖，不只这些大表）：
- 7,800 个角色分布账号，3,000 名学生；一个容量租户外另保留双租户/同租户他人访问负例。
- 300 万 turn、600 万消息、30 万会话；每 turn 平均 80 个持久事件，合计 **2.4 亿 turn events**。
- 120 万题库条目、600 万学习交互；平均每交互 8 个领域事件，即 4,800 万学习事件。以上学习量按 50% 学生日活计算，与全体 100% 日活的上界分开。
- 60 万阅读引用及 600 万阅读记录，按全体学生历史累积预留；至少覆盖 1 万共享材料、6 万个人材料的逻辑规模。共享条目只有已有授权业务支持时才能共享，不为造容量伪造 grant；实际源不共享的载荷按实际副本计数。
  - 阅读记录是逻辑业务计数：按最终实现分别统计 PG 目录行与既有标注/笔记/进度文件载荷，二者都验收；不为凑行数新增无人消费的 PG 表，也不因文件不在 PG 而漏测其容量。本 change 不自动迁移全部 JSON/Markdown 的范围保持不变。
- 额外植入上述重度单用户、教师共享热点、集中班级提交、长消息/工具结果和失败/撤权样本；不能只把同一短 JSON 重复填充为可高度压缩的“海量数据”。
- 80 events/turn 是未实测假设：分别用 20、80、400 events/turn 做敏感性分析，长流程另覆盖 1,000 events/turn。最终用真实模型样本校准分布，不能为了达标删除事件或破坏 replay/trace 语义。

三年容量规划：常态约 1,800 万消息，高活跃约 3,600 万消息；P2 为对应 P1 的约 10 倍，须在扩容放行前实测。**本 change 首次容量通过范围为 P1 一学年与重度尾部，不把三年/P2 外推写成已验收。** 三年是用于容量敏感性分析的历史长度，不是批准所有类别统一保存三年的隐私政策。

## 3. 存储预算：事件、文件、检索与备份分开

当前源码事实：`services/session/turns/configured.py:_configured_event` 对流事件持久化后再发布；`persistence/postgres/session.py:finalize_turn` 保存最终消息和终态事件。现有普通 executor 保存 assistant message 时传入 `events=[]`；因此不能武断声称当前每个事件又完整重复存进 messages。旧导入 payload/兼容字段若含重复事件，要按实际源计量，不能未经许可删掉。

示例计算（十进制 GB/TB；KiB=1024 字节）：
- 每 turn 两条正文合计 6 KiB、turn 等状态 1 KiB、80 个事件每个平均 0.75 KiB：`300万×(6+1+80×0.75) KiB ≈ 206 GB` 原始逻辑载荷。
- 再加题库、学习/阅读及审计等约 35–50 GB 逻辑载荷；行开销、索引、TOAST/压缩的净倍率暂用 1.5–2.5 估算，须实际测量。
- **P1 常态应用 PG 约 0.35–0.65 TB/年；高活跃约 0.7–1.3 TB/年。取整规划区间 0.3–1.5 TB/年，三年约 1–4.5 TB。** 这不含 WAL、临时排序、维护空闲空间、备库和备份；事件若更密集/工具结果更大还会超出区间。
- 单学生每活跃日 2 张、平均 1 MB 的作业图：`3000×50%×200×2×1 MB = 600 GB/年`。加共享 PDF、个人文档、导出及解析派生物，**P1 文件初步按 1–2 TB/年**预留；持续音视频单列码率×时长×使用者，不能塞进此估算。文件属于 S3/资源工作线，不因 PG-only 要求把大文件塞进 PG。
- LightRAG 检索 PG、HugeGraph 图与模型 embedding 索引不包含在应用 PG 上述数字中；A2 按去重文档/chunk/向量维度/索引与派生版本独立实测。共享教材只存一份原文，并不意味着各授权 workspace 的派生索引只有一份。
- PG 备库、备份保留与恢复暂存各自预算；不是给主库容量乘一个模糊倍率后宣称 HA/恢复完成。维护可用余量暂取至少 30%，导入还须同时容纳 staging、promotion、WAL 与失败恢复空间，以实测峰值决定能否开工。

测量时用 `pg_total_relation_size` 汇总表、索引与 TOAST，并另计数据库总量和 WAL，不只统计正文长度；该函数的范围见 [PostgreSQL 17 文档](https://www.postgresql.org/docs/17/functions-admin.html)。这里 1.5–2.5 倍是我们的估算，并非 PG 官方保证。

心理/家庭/生涯敏感内容的容量规划不授权长期留存、跨角色查看或采集真实样本。长期学习档案摘要、原始私密对话、工具 trace、审计与备份应分别制定可验证的保留/删除和访问策略；本次不擅自设置清理任务，不把“支持 K12 全周期”解释为保留 12 年全部原文。

## 4. 高峰：四种并发不能混淆

| 指标 | P0 | P1 首期目标 | P2 规划目标 |
| --- | ---: | ---: | ---: |
| 同时在线/长连接 | 60 | 600 | 6,000 |
| 普通业务 API 持续负载，不含模型流事件 | 30 req/s | 300 req/s | 3,000 req/s |
| 普通 API 五分钟突发 | 60 req/s | 600 req/s | 6,000 req/s |
| 新 AI turn 到达率（持续） | 0.5 turn/s | 5 turn/s | 50 turn/s |
| 新 AI turn 五分钟突发 | 1 turn/s | 10 turn/s | 100 turn/s |
| 若平均 30 秒结束，持续在途 AI turn | 15 | 150 | 1,500 |

- 在途数估计为 `到达率×平均处理时长`，不是用 p95 代替均值。P1 突发约 300 在途 turn；若变为平均 90 秒则持续约 450 在途，必须独立设置长流程准入/排队，不能按短答假设无限放行。
- 这些是有余量的压测形状，不是从年度平均数除以全年秒数得到的生产预测。P1 的 600 在线每 4 秒操作一次约 150 API req/s，持续 300 req/s 留出突刺/其他角色操作空间。集中提交还测单班 50 人在 10 秒内提交及并行多班，不能只用均匀随机请求。
- P1 5 turn/s、80 events/turn 约 400 次事件追加/s；400 events/turn 时为 2,000 次/s，还要加身份重验、事务、索引、审计等开销。API req/s 不等于 SQL QPS，二者分别记录。
- PG 连接只服务短事务，不应在模型生成/等待用户答复期间独占。总连接预算是所有进程同步池+异步池+后台/渠道池+运维预留之和，不能给每个在线学生分配连接。现有配置默认池大小不是容量结论，须观察池等待再选值。
- 如果每 turn 平均 1.5 次物理模型请求、每请求输入 4,000/output 1,000 tokens，P1 持续档约 **450 RPM、225 万 tokens/min**；仅为配额核算示例。真实上下文长度、模型重试/工具调用和供应商配额分开校准。“模型费用暂不设上限”不等于供应商允许无限并发。
- P2 不是自动允许多 worker/多执行者：当前 H 单执行门禁保留，启用多执行/HA 须 G-H。容量租户数量也不授予正式多租户发布许可。

## 5. 性能与可靠性目标

普通接口在完整 PG、真实索引、RLS、身份校验及混合读写下计量，不关闭安全检查达标。按用户旅程和请求类型分开设 SLI/SLO，而不是只看数据库平均耗时，这一方法参照 [Google SRE：Implementing SLOs](https://sre.google/workbook/implementing-slos/)；下表具体阈值由本项目提出，不是该资料给出的行业标准。

| 路径/指标 | v1 目标 | 测量边界 |
| --- | --- | --- |
| 历史/题库/阅读分页、进度查询 | p95 ≤300 ms，p99 ≤1 s | API 收到请求至完整响应，含认证/池等待/序列化；默认受限页长，不含公网传输 |
| 作业/答题/笔记/进度保存 | p95 ≤500 ms，p99 ≤1.5 s | 已持久提交后的成功确认，不把排队受理当保存成功 |
| 内容搜索、班级统计 | p95 ≤1 s，p99 ≤3 s | 固定查询集合与真实过滤/权限；复杂导出单列后台吞吐 |
| 池获取等待 | p95 ≤50 ms，p99 ≤200 ms | 同步/异步/渠道池分别记，不能用 SQL 均值冒充 |
| P1 持续档业务请求成功率 | ≥99.9% | 合法请求中失败/超时计入；429/503 不能靠从分母删除达标；越权负例单列 |
| 普通 AI 首个有效答复 token | p95 ≤5 s（后续产品目标） | 客户端发起至首个有内容 token，排队也计入；状态/心跳不算首字 |
| 普通 AI 完整短答 | p95 ≤30 s（后续产品目标） | 约 1,000 output tokens 的固定普通问答集，和首字分别计量 |
| 深度解题/规划等长流程 | 1 s 内受理/状态；持续进度可见 | 不套 30 s 短答线，分阶段记录耗时/失败/取消与排队 |

P1 突发档允许普通接口延迟目标至持续档的 2 倍，但成功率不降低；超出声明容量的阶梯测试允许明确受控拒绝，仍须零数据丢失、零越权、无重复外部动作，停止突刺后 2 分钟内恢复持续档。这里恢复指压力恢复，不是故障恢复 RTO 承诺。

对可观察的业务写入，测试必须零静默丢失/重复确认，错误与取消可核对。在线可用性、灾备 RPO/RTO 和敏感场景人工处理时效不由一次压测证明，仍归相应 H/G1/业务安全门禁；不能把普通聊天通过当作心理支持产品质量验收。

## 6. 导入时长与具体通过方式

建议首次受控导入预留**一个夜间维护窗口：P1 一学年全结构化数据总流程 ≤8 小时，其中最终跨全部领域单事务 promotion ≤2 小时**；10 GB/至多 1,000 万行的代表性小数据集目标 ≤30 分钟，重度单用户集目标 ≤15 分钟。它们是独立测试档，不可用小档外推宣称 P1 达标。时间包括停写确认、一致快照、摘要、prepare/staging、全量内容/引用核验、promotion 和业务 smoke；不允许省掉核验换吞吐。

该窗口假设源与目标验证环境同区域、文件载荷已按资源契约就绪；若还需跨网搬运文件，必须另实测并加入总停写窗口，而不是在报告中藏掉。重做 OCR/embedding/图索引不是数据库导入本身，A2 独立验收后才谈全产品迁移窗口。此建议不授权操作真实旧库/选定生产停写时间；正式 cutover 仍需真实清单与批准。

执行 task 1.47 时：
1. 固定 build/schema/PG 与驱动版本、操作系统、CPU/RAM/磁盘/网络、PG 参数和各池预算；记录生成器 seed、全部表行数/字节与场景分布。先核对磁盘余量，不在开发机无预检写入 TB 合成数据，也不为此擅自采购或启动付费基础设施。
2. 在隔离真实 PG 按 P0→P1 递增准备。历史数据可用受控批量装载提速，但在线压测必须走实际 provider/API，不能直接 SQL 插入速度充当产品速度；runtime 禁止 SQLite，离线源仅在隔离 importer 进程。
3. 热点/长尾和双用户、跨租户负例一并执行；分别报告冷启动与热缓存。建议预热 5 分钟、持续档 30 分钟、突发 5 分钟及恢复，关键结果重复 3 次，不能只选最好一次。
4. 流事件压力可以使用不付费的协议负载生成器，但必须实走 PG 事件/重放/提交路径并清楚标为“持久化容量”，不冒称真实 AI 端到端容量。task 2.5 用授权模型验证真实行为并校准事件/token/延迟分布；真实供应商并发能力须另有相应负载证据。
5. 分操作记录吞吐、p50/p95/p99、失败/超时/排队、池等待、连接/事务、锁等待、WAL/临时磁盘与进程峰值 RSS。进程 RSS 必须在有界并发/批量下收敛，不能随全部历史行数线性增长；先在小档记录冷基线与并发峰值，再把运行内存限制作为固定测试参数，不先承诺某型号机器一定够。
6. 分页用有界页长/稳定游标；导入初始批量建议 `≤1000 行且≤8 MiB`，遇大行按字节收缩并验证已支持的大载荷，不静默丢弃。最终 promotion 仍是全域单事务：prepare 分块不允许变成部分公开提交。
7. 记录真实导入全流程和 promotion 各耗时、峰值 staging/WAL/磁盘、取消后恢复与重复运行。若 P1 不能在目标资源/窗口完成，明确失败原因和调整方案，不悄悄把数据缩小或放宽阈值后勾选。
8. 当前环境若只完成 P0，报告“P0 已测 / P1 未测”而不是 1.47 完成。P2、三年存量、S3/RAG 与 HA 是明确后续放行范围，不能从 P1 线性推算成性能保证。

## 7. 评估状态

- 已完成：需求场景→假设→数量→存储敏感性→验收阈值的评估；核查当前流事件持久路径及既有企业存储/单执行边界。
- 尚未完成：上述 P0/P1 实际造数、容量压测/导入计时、模型分布校准；没有新增模型调用、读取真实学生数据或改动业务保留策略。
- 两周真实试点观测后复核日活、轮数、上传量、事件密度与高峰集中度；调整容量模型须保留前后假设和测量，不用“架构支持”代替证据。
