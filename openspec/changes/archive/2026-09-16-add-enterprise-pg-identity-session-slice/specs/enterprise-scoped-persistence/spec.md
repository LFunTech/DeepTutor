## Purpose

规定企业身份与会话数据的应用 PostgreSQL 持久化和可信范围契约，确保固定单租户首个切片就能防止同租户私有内容越权、跨租户连接复用和错误迁移，并为后续企业领域提供稳定内部标识。

## ADDED Requirements

### Requirement: 稳定内部身份和复合归属

系统 SHALL 使用内部稳定 tenant/user/session/turn 标识，租户级记录具有非空 tenant 和适用的 owner/复合唯一键/外键；外部身份、展示名称或物理路径不得决定资源主键。会话父子关系和事件/消息关联 MUST 验证同一合法会话与所有者。

#### Scenario: 跨范围构造关联
- **WHEN** 写入的 message、turn、parent 或 owner 指向另一租户或未授权用户的记录
- **THEN** 事务拒绝且不留下部分关联，不能只凭资源 ID 存在或 tenant 相同放行

#### Scenario: 同名或同用户标识的不同测试租户
- **WHEN** 两个隔离测试租户使用相同用户名、相同 user ID 或相同会话测试 ID
- **THEN** 数据、唯一约束和授权按完整 scope 区分，不因名称冲突合并身份或资源

### Requirement: 事务级租户隔离和受限运行角色

租户表 MUST 启用并强制数据库行级隔离，运行身份 MUST 不是表 owner、superuser 或具有 BYPASSRLS 的角色。每次操作 SHALL 在同一显式事务/连接安装可信局部 scope，业务层同时执行 owner 检查。

#### Scenario: 连接池复用或事务取消
- **WHEN** 请求完成、回滚、超时或取消后，连接被另一个 tenant/user 复用
- **THEN** 新请求不继承旧 scope、未提交写入或权限，缺 scope 的普通数据访问被拒绝

#### Scenario: 绕过业务查询条件
- **WHEN** 受限应用身份直接执行无 tenant 过滤的读写或试图写入其他 tenant
- **THEN** 数据库仍限制在可信事务 tenant；同租户 owner 负例另经业务服务验证，不能用 RLS 代替个人授权

### Requirement: runtime 与后台范围不可串用

缓存、会话运行实例、事件订阅和恢复任务 SHALL 使用包含 tenant/owner 的稳定 namespace，不以文件路径、仅 user ID 或默认 scope 索引。后台身份枚举与恢复 SHALL 来自受控持久记录，不回退全局管理员连接。

#### Scenario: 交错执行多个用户请求
- **WHEN** 两测试租户及同租户两个用户在同进程交错发起、订阅或控制 turn
- **THEN** 各请求始终使用本人的 scoped runtime；请求结束/异常后不残留 ContextVar 或可变单例身份

#### Scenario: 后台处理缺失或已失效身份
- **WHEN** 恢复/重试记录缺少可信 scope，或用户/租户已失效
- **THEN** 不执行用户业务副作用，不降为 local admin；必要状态清理仅由用途受限的系统操作完成并留审计

### Requirement: 版本化迁移与运行职责分离

应用 schema、索引、约束、默认数据 SHALL 使用版本化迁移和受控初始化流程，保留历史、互斥和漂移检测；运行进程 MUST 仅校验兼容性，不在每个启动中高权建表/补数据。本切片 MUST 不执行检索库、图库或外部身份系统迁移。

#### Scenario: 重复或并发执行迁移
- **WHEN** 同一版本重复执行，两个迁移任务竞争，或发现已应用版本内容漂移
- **THEN** 已应用版本不重复产生数据副作用，竞争受互斥保护，漂移或失败阻断接流量并记录实际状态

#### Scenario: 运行用户尝试 DDL
- **WHEN** 应用运行身份试图创建/修改 schema、角色或关闭租户防线
- **THEN** 数据库拒绝，不能临时提权或用本地库继续服务

### Requirement: 故障恢复与旧数据不自动迁入

PG 失败 MUST 使相应操作明确失败且不虚报持久化成功。备份恢复 SHALL 验证本切片账号、权限、历史及事件引用一致，并执行身份恢复门禁，不能使恢复点后的退出、禁用或凭证撤销被旧快照覆盖。真实旧数据迁入须另有归属/备份/只读导入批准，不因本切片初始化自动扫描或改写用户现有文件。

#### Scenario: PG 中断后恢复
- **WHEN** 事件或最终消息提交失败、进程重建后恢复相同 PG 数据
- **THEN** 已提交数据仍可读取，未提交结果不显示为已持久化成功，在途失败状态可解释且无 SQLite/file fallback

#### Scenario: 新库已有写入后需要回退
- **WHEN** 企业应用需要回退版本
- **THEN** 只能使用兼容当前应用 schema 的版本或受控停写恢复，不能切回旧 SQLite 丢弃新数据
